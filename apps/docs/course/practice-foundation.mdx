# Practice checkpoints · Lessons 1–16

Each lesson below has a **reference checkpoint**: a complete, runnable Godot
project showing one honest end state. Create it from a fresh clone, open it
beside your own blank project, and compare when you are stuck. The checkpoint
is a mirror and a parts shelf — study it, and take whole files from it only
as the rule below allows. The creation command refuses non-empty folders so
you cannot overwrite yourself by accident.

```bash
node scripts/course-create.mjs --lesson 5
node scripts/course-create.mjs --lesson 8 --out builds/course/lesson-08
node scripts/course-create.mjs --list
```

Outputs default to `builds/course/lesson-NN/`. Open the output in the editor
once before any command-line run so it imports (Godot 4.7.1 minimum, 4.7.2
recommended — see [Godot version](/course#godot-version)). Checkpoints use
the reference identity `Moonlit Course Reference` /
`com.example.moonlitcourse.ref`: three namespaces stay separate — your own
blank `Moonlit Course` project, the generated reference, and the installed
shipping Moonlit Beacon — so a reference save or install can never
overwrite your work or the game.

Every checkpoint below lists its goal, the exact files it adds or changes
against the previous lesson (each name opens its complete published
source), the editor steps in short form (the lesson itself tells the full
story), one independent modification, and the observable change that proves
you understood it.

All file paths below are relative to the checkpoint root (for example
`builds/course/lesson-05/`). Each linked source also sits in your clone
under `examples/course/src/` (lesson layers) and
`examples/course/src/assets/` (art, audio, font) — the links open the same
published files, and the same checkpoint-relative path under your generated
`builds/course/lesson-NN/` is the offline equivalent. Work each lesson in
this order: create the checkpoint; build every listed file from the lesson
first — and where the lesson leaves construction details out (the Lesson 2
forest scenes are the known case), create the NEW file from the linked
complete source instead of guessing. When you replace a file you already
built, commit or back it up first and apply only the named changes; never
bulk-overwrite your whole project from a checkpoint. Then open the scene or
script in Godot, read its nodes or key behavior against the lesson's
explanation, and finish with the lesson's Modify exercise. Generating the
checkpoint is the mirror, not the learning: build, explain, modify, verify.

## First actions — engine, clone, reference, learner project

Do these four once, in order, before Lesson 1. Steps 1–3 run on your
machine outside Godot; step 4 is in the Godot editor.

1. **Install the engine.** Godot 4.7.2 Standard recommended, 4.7.1 minimum
   (see [Godot version](/course#godot-version) for the exact archives).
   Installing Godot does not put a `godot` command on your PATH — remember
   the executable's full path; quoting it handles the spaces.
2. **Clone the repository fresh** into its own folder, and install Node.js
   20+ for the helper scripts (no `pnpm install` needed — they use the
   Node standard library only):

   ```bash
   git clone https://github.com/hyodotdev/MoonlitBeacon.git
   cd MoonlitBeacon
   ```

   The clone already contains every selected playable asset and all
   sixteen lesson layers under `examples/course/src/`.
3. **Create a reference** from the clone root. This command exists only in
   the clone — never type it in your blank project:

   ```bash
   node scripts/course-create.mjs --lesson 1
   ```

   It writes a complete standalone Lesson 1 project to
   `builds/course/lesson-01/`. Substitute `--lesson N` (1–16) per lesson,
   or `--out` with a NEW or empty folder of your own; the creator refuses
   to touch existing work, source folders, or symlinked paths.
4. **Make your separate learner project** in the Godot Project Manager:
   `+ New` → name `Moonlit Course` → empty folder *outside* the clone
   (Lesson 1 uses `~/moonlit-course/my-game/`) → Renderer: Compatibility.
   This blank project is where you follow every lesson. Its identity stays
   separate from the reference (`Moonlit Course Reference`, package
   `com.example.moonlitcourse.ref`) and from the shipping game, so saves
   and installs can never collide.

## How the checkpoints differ from the historical clips

The clips show the original build; the checkpoints are a simplified,
runnable reconstruction of the same lessons. Honest differences:

- The title is the minimal nine-node scene, and the Lesson 2 forest is
  about twenty nodes — not the historical 1,296-node screen. There is no
  mist, vignette, canopy, motes, smoke, or embers; one flame system plus
  glow and light carries the fire.
- Values the lessons never state are practice choices, written plainly in
  the source: `BGM_SILENCE_DB` −80, `WALK_THRESHOLD` 8.0, `CHARGE_SECONDS`
  2.0, spirit `speed` 52.
- The lesson text calls `AudioStreamPlayer.release()`, which does not exist
  in Godot 4.7 (verified by probe: `has_method("release")` is false on both
  player types). The checkpoints stop players through the shared
  `AudioFlush` helper instead.
- The font is the tracked, attributed MapleStory Light — not Galmuri, whose
  font file is no longer tracked. Collision values keep the lessons'
  numbers: mask value 2 is inspector checkbox 2, value 4 is checkbox 3.
- Every translated string calls `tr()` explicitly and redraws on
  `Settings.changed`. A scene's stored text keeps its key in the property;
  the checkpoints never rely on draw-time lookup a headless test cannot
  read.
- The `Music`/`Sfx` buses are created in `Settings._ready`, not in a bus
  layout file. Panels, players, and volumes are the same; only the
  creation site differs.
- The reference export preset sets `package/signed` with empty keystore
  fields and the `.ref` package: signed by the local debug key at export
  time, never by a committed credential. The release keystore, store
  steps, and any actual APK/device run stay the learner's own procedure
  in their own project — nothing here publishes.
- Phone multitouch, Android exports, signing, and future engine versions
  are not verified by the desktop checks. The checkpoints prove the
  desktop path; the lesson's device steps remain yours to run.
- A forced engine quit (`--quit-after`) still tears down with music
  playing and leaks voices: the engine never delivers `close_requested`,
  so no production handler can run. That is a harness limitation, not the
  player's path — a real window close or the Lesson 16 Yes button goes
  through the graceful quit above, and the checks prove it clean.
