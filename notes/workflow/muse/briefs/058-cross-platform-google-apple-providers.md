# Brief 058: The same Google and Apple account on either mobile platform

## The ask
“구글 게임 로그인 애플로그인 게스트 로그인 넣고 ... 마지막 플레이 ... 계속 이어가게”, and the supplied Android title shows Google, Apple and guest. Default product choice is all three on Android and iOS, so a player can actually carry one account between devices. Presentation and owned journey orchestration are separate tasks.

## Where things stand
Native identity currently supports Play Games authentication only on Android and native Apple authentication only on iOS. Android Debug/Release compilation is director-proven; the director is finishing real iOS compile/export checks. Public ID durability, guest sessions, operation locks, cancel/draining semantics and account conflicts already have meaningful tests. Preserve those. Firebase provider setup is not enabled and credentials are never available to your copy.

## Do
- Implement ordinary Google account authentication as the shared Firebase `google.com` identity on Android and iOS. Android uses official Credential Manager/Google ID SDK and Firebase GoogleAuthProvider; iOS uses official GoogleSignIn SDK and FIRGoogleAuthProvider with complete URL callback/export configuration. Use real pinned official SDK versions, checked against local headers/metadata and official documentation supplied below. Primary Google identity must be the same provider on both OSes. Preserve Play Games v2 as an optional gaming-profile connection or separately named provider, without silently merging its distinct `playgames.google.com` account with `google.com`, making it a prerequisite for guest/Google play, or claiming it gives iOS the same Firebase UID automatically.
- Add Android Apple authentication using Firebase's supported OAuthProvider `apple.com` browser flow, with correct pendingAuthResult/lifecycle handling, cancel/draining locking, credential linking and reauthentication. Keep existing iOS native Apple/nonce flow. Provider readiness gates separately: missing Google config does not block guest or Apple, missing Apple setup does not block Google. Public client ID/URL scheme and enabled readiness flags may be staged; all secret/private Apple/OAuth material stays server-side and never enters the app.
- Extend the build templates, configuration preflight, artifact checks and export hooks for these exact SDKs and callbacks. Godot iOS callbacks must preserve existing app/IAP handling; inspect the actual engine/plugin integration rather than assuming an app delegate exists or patching generated files by hand. Link all transitive SDK frameworks/resources and preserve original privacy bundle bytes. Guest linking keeps the Firebase UID; linking elsewhere produces an explicit conflict without deleting or overwriting the guest. Never auto-link one social provider to another without the host's explicit player action/consent.
- Add meaningful native/wrapper/build tests for both provider capabilities on both platforms, configuration independence, stable UID link, conflict, stale/cancel/timeout/draining, callback forwarding preserving the existing delegate, and complete export composition. Report exact official dependency pins and setup steps. The director runs real AAR and arm64 bridge/game export builds. Do not claim provider/device authentication from fixtures.
- Provide a public `NativeIdentityAdapter.refresh_native_session()` method forwarding the bridge's real `get_session` through the existing outcome folding, leaving `get_session()` as a memory snapshot (it is used inside signal emission, so making it query natively would recurse). The production host's `PlayerAccount.refresh_session` can call this method when present. Prove SDK-restored sessions hydrate the adapter after process restart, including asynchronous/signed-out results, without performing a new provider sign-in or showing UI. Extend the base/fake adapter contract if necessary. Do not rewrite PlayerAccount here.

## Primary sources for the integration contract
https://firebase.google.com/docs/auth/android/google-signin — Credential Manager plus GoogleAuthProvider; examples pin credentials 1.3.0/googleid 1.1.1. Keep already measured compatible Firebase/Godot/Kotlin pins unless a real build requires a change.
https://firebase.google.com/docs/auth/ios/google-signin — GoogleSignIn headers, reversed-client-ID URL scheme, handleURL forwarding, FIRGoogleAuthProvider.
https://developers.google.com/identity/sign-in/ios/start-integrating — official iOS SDK integration.
https://firebase.google.com/docs/auth/android/apple — OAuthProvider, pending result, SDK browser flow, reauth/link requirements, server-side Service ID/key configuration.
Do not copy the documentation's logging of tokens/user profiles. App code never reads/saves/logs personal name/email/token, except an ID token returned only to the in-memory transport supplier. Firebase/provider may process account data as part of authentication; describe it truthfully in setup notes.

## Do not
No PlayerAccount public-ID persistence rewrite (the production host task owns canonical-ID/account partition wiring), gameplay/UI/cloud/arena, protected/locked project/presets, shared runner/package, credentials/network/device/store/git-history operations. No manual OAuth credential fabrication, metadata suppression, billing upgrade or mock-success production fallback.

## Judgment
Director builds both Android variants and arm64 iOS libraries with real SDK products, checks actual generated game manifests/URL callback/extension/IAP composition, runs focused tests and a negative guard control. Production buttons must be truthful about configuration; after the user's server setup, genuine device login is a separate required evidence item. One Google account must use the same Firebase provider on either platform, one Apple account likewise.
