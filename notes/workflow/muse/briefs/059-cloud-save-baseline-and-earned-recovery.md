# Brief 059: Preserve remote progress and unpaid local earnings

## Confirmed director evidence
The director reproduced all 589 coordinator cases cleanly, then tested three missing production interleavings with real isolated Journey/Vault files and the same injected transport.

1. Local account has no acknowledged revision, local checkpoint 5/cycle 3. The remote already has revision 5/checkpoint 6/cycle 5 before the GET. With an ordinary successful commit reply, `flush` returns `ok`, commits the local payload as revision 6, and never signals conflict. `_flush_async` reads the latest remote revision and silently rebases onto it. Compare-and-swap only protects changes after that GET; it does not protect progress from another device made before it. The persisted acknowledged revision currently never guards this case.
2. A locally issued integer journey has a verified local checkpoint echo of 15 earned shards, with no successful Vault settlement yet. Reconfiguring after restart calls `_reconcile_active_receipt_floor`, records all 15 as a zero-grant floor, then `settle_journey_receipt(issued, 2, 15)` grants zero; bank remains zero. The coordinator treats unpaid local earnings as foreign remote history. This breaks the accepted failed-settlement retry guarantee. Local reconciliation must preserve and recover legitimate unpaid earnings exactly once; only imported remote history is zero-grant floored. Unknown retired receipts must still never mint.
3. The first seal is taken for upload. During its commit callback a second verified seal lands locally and queues. `CloudCheckpoint.save_revision` clears it because every queued revision is 1 and `1 <= next_revision`. Result: `acked`, `has_pending=false`, while local checkpoint is 2 and the uploaded payload is checkpoint 1. Preserve the newer pending payload and serialize/coalesce flushes; do not report it acknowledged until its own server commit. Reconfiguration during internal checkpoint awaits must not clear or mutate the new account's pending state either.

Operational probe output is retained under the director's ignored verification files. These are confirmed defects, not hypothetical requests.

## Do
Fix these three interleavings, extend permanent focused tests with ordinary successful replies and durable file/restart cases, and keep conflicts explicit until the player chooses. A remote revision/payload differing from the durable local sync baseline is a conflict before committing; a not-found document with previously acknowledged history is also a meaningful conflict/state, not silently overwritten. Capture the baseline with pending work; never silently change it on retries. Preserve both versions for explicit choices and recovery. Explicit local choice must preserve the actual freshly-read rejected remote if it advanced again after the dialog opened.

Keep local integer/fallback failed-settlement retry meaningful across restart. Maintain trustworthy distinction between locally earned pending value and imported zero-grant remote history. Do not repair this by granting unissued/evicted receipts or removing the floor. For imported numeric receipt IDs that can collide with an existing local/other-account ID, document and test the safe identity mapping contract needed by the host; do not silently alias unrelated receipts or corrupt an existing record. If a checkpoint schema adjustment is necessary, retain backwards compatibility and tell the director the exact host changes required.

Ensure in-flight old payload completion cannot erase a newer seal, restore, or account's state. Global coordinator generation guards must cover mutations within awaited helpers, not only the outer completion. Use a single bounded flush owner with the latest coalesced pending work. No spin/retry storm, per-frame work, or network wait on gameplay.
