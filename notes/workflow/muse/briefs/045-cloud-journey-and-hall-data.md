# Brief 045: Owned cloud journeys and character Hall of Fame data

## The ask
The user requested 4.0.0 Google/Apple/guest accounts, continuation from the last gate, and ongoing rankings showing the character, score and a unique player ID. This round supplies the cloud data layer; title/HUD integration follows after the independent journey/native/art rounds.

## Where things stand
The main working tree still has the 3.0.0 runtime. Independent copies are implementing local Journey checkpoints and native identity. Do not import their files or change their ownership areas. Existing `firestore.rules` supports legacy `/scores` and opt-in analytics, and denies everything else. `FirebaseConfig` identifies the existing project but no client configuration is present. Native identity will provide Firebase UID and an in-memory ID token; its stable public ID uses `MB-` plus 32 lowercase hexadecimal characters. No Firebase provider is enabled yet. Director setup, network, deployment and device checks are separate operations. Keep the existing Spark plan; no Cloud Functions or billing upgrade.

## Do
- Add new independent Godot cloud service/transport modules, using Firebase-authenticated Firestore REST and injectable request transport/token supplier. Do not save or log tokens, email, provider names or auth codes. Bound response bytes, request timeouts, retries and request concurrency. Explicitly report offline/unconfigured/cancelled/conflict/failure states. Late replies for an old account or request cannot apply to the current player.
- Reserve a collision-resistant public ID with an immutable private UID-to-public-ID profile and a matching ID reservation in one atomic commit. A restored cloud account retrieves its canonical ID; linking a Firebase guest keeps the same UID/ID. Never claim offline IDs are globally reserved. A collision retries safely before registration success; another UID cannot claim or change an existing ID. Account switching must not overwrite the prior account's local journey.
- Read/write one private versioned checkpoint per UID, with bounded journey payload, integer revision and compare-and-swap precondition. Queue only stable checkpoint notifications (integration is later), coalesce changes, retain failed saves for retry, and never claim cloud success before acknowledgement. Present a conflict result carrying safe local/remote summaries rather than silently choosing a clock timestamp. The integration can explicitly choose local or remote. A downloaded payload still needs the Journey validator before gameplay applies it. Do not sync paid entitlements or Vault purchase/earned currency ledgers.
- Keep a public best-score record per public ID for 4.0.0, including the allowlisted hero path/id, score, cycles, release/schema, and server update time. Updates are monotonic and idempotent; retries cannot mint another player row. Allow owned record deletion. Supply top-board query and actual self-rank by aggregation/count; ties may share a rank. Cache/throttle live read requests and label cached/local data distinctly. No fake population or claim of authoritative anti-cheat; structural score bounds cannot prove gameplay legitimacy.
- Extend Firestore rules only with new namespaced collections for those profiles, reservations, checkpoints and Hall records. Keep legacy 3.0.0 score/analytics contracts unchanged. Only the authenticated owner reads a private save, creates/updates their records, or deletes their data. Public Hall rows expose no email, private save or credential. Deny UID/ID reassignment, cross-owner writes, stale revisions, extra fields, decreasing scores, invalid hero paths and oversized payloads. Supply indexes for the actual queries and an account-data deletion plan that runs before deleting Firebase Auth so records are not orphaned.
- Add standalone Godot transport/data behavior tests plus real Firebase Rules emulator tests and a reproducible command to run them. No external emulator download now: the director supplies official dependencies later. A static source test is not rules execution. Add an author-only cloud schema/setup note listing exact deployment and readiness steps and actual collection field contracts.

## Do not
Do not change existing arena/title/result/ladder UI, journey/onboarding/story, identity modules/addon, art, project/presets, package.json, existing regression runner, stores, credentials, guards or workflow files. New modules/tests/tooling and additive Firestore rules/indexes only. Never deploy, upload, sign in to external services, add billing, or perform device operations. Do not claim production cloud support from mocks.

## Acceptance and judgment
Focused tests reproduce registration collision, canonical-ID restore, preserved guest link identity, bounded retries, stale callback/account isolation, failed save retry, explicit revision conflict, monotonic unique best score and deletion ordering. Emulator tests prove unauthenticated and cross-owner access are denied while valid owner operations succeed and legacy contracts remain intact. Director repeats these against the real emulator, reviews the REST requests/rules/indexes and runs a negative control. Report source/mocked/emulator/deployed-provider evidence separately, with exact runnable commands and changed files.
